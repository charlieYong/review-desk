# 共享批注与项目文档归属修复记录

本次只修复跨客户端共享批注和项目文档归属两个问题。保留现有预览服务、文件入口、手动开启审查轮次和历史意见流程；未引入账号、数据库、实时协作框架，也未搬迁历史文档。

## 运行环境核实

- 实际服务由用户级 `html-preview.service` 管理，执行 `/home/<用户名>/.local/share/html-preview/server.py`，内容目录为 `/home/<用户名>/html-preview`，监听 `0.0.0.0:8088`。示例中的用户名、服务器 IP 为占位符。
- 对应源码仓库为 `/home/<用户名>/charlie/review-desk`，修复前工作区干净，HEAD 为 `aad9d89`。安装目录是独立文件副本，不是仓库的符号链接；修复前 `server.py`、`review.html` 与仓库逐字节一致。
- 修改保存在源码仓库，同步必要运行文件到原安装目录，再通过现有 systemd 服务重启。未改服务入口、端口或内容目录。共享数据默认写入安装目录的 `data/`，也可通过 `--state-directory` 指定；更新程序时保留该目录。
- `.codex/AGENTS.md` 与 `.claude/CLAUDE.md` 均指向 `.agents/AGENTS.md`。生效的是这一个用户级文件，不是本项目 README 中的配置模板。

## 问题一的根因与链路

修复前，`openPage()` 用 `review-desk:v1:` 加完整浏览器 URL 读取 localStorage，恢复当前轮次、意见和历史。保存、删除、修改和开始新轮次都只通过 `persist()` 回写 localStorage；测试捕获到的保存请求为零。服务端只提供文档正文和内容指纹，没有批注读取或写入接口，也没有文档与轮次的共享状态。

因此，同一链接在两个隔离浏览器中也不共享意见。浏览器刷新只恢复自身数据，分享链接只分享入口。键还包含 origin 和具体路径：直接使用普通路径和 `/_fs` 路径访问同一文件时会产生两套本地数据。已有 `locate` 接口虽能将内容目录内绝对路径转成普通入口，但不能修复已经存在的直接链接和旧数据。不同目录同名文件原来按完整 URL 区分，这一隔离语义继续保留。

### 最小实现

1. `server.py` 复用原 `resolve_document()`，将普通路径和绝对路径都解析为真实文件路径。`review_store.py` 以 `source.resolve()` 的完整绝对路径识别文档，符号链接归一、查询参数忽略，同名异目录隔离。存储文件名使用文档路径摘要，JSON 内仍记录文档身份。
2. `GET /_preview/review?page=...` 读取共享状态，返回文档身份、规范入口、状态版本，以及 `round`、内容 `revision`、`entries`、`archives`。首次读取即持久化初始轮次，避免无批注时不同客户端因文件更新获得不同的本轮版本。
3. `POST /_preview/review` 提交单条新增、编辑、删除、历史解决状态、开启新轮次或旧数据导入。前端只在服务端确认成功后清空草稿。新增按 ID 去重；独立新增和不同意见的修改互不覆盖。同条编辑、删除或解决状态比较客户端原意见，过期操作返回 HTTP 409，页面读取最新共享状态并保留草稿。
4. 每次提交在单服务进程的锁内读取最新状态、校验并修改；先写临时文件、flush/fsync，再原子替换。不会用整个客户端旧快照覆盖其他人的意见。保存失败不会返回成功。
5. 每条操作携带当前轮次与内容版本。开启新轮次在锁内一次归档所有已提交意见，再切换版本并清空本轮；并发新增若先提交则进入归档，若晚于切轮则明确冲突。内容指纹仍基于源文，只有时间变化不触发更新，更新不会自动开启新轮次。
6. 打开、刷新、切回可见窗口或可见页面每 15 秒读取共享更新，无即时推送。有草稿时保留草稿；其他客户端切轮后提示核对，避免把旧正文意见悄悄保存到新轮次。历史的解决、继续跟进、重新选段、汇总流程保留，历史仍不保存完整旧正文。

### 原有本地意见

打开文档时，读取当前 origin 可访问的旧 localStorage 键，通过现有定位接口确认它们指向同一真实文件，再导入旧数组或包含轮次与历史的对象。普通路径和绝对路径两套旧数据都能进入共享状态，原 localStorage 不修改、不删除。

首次导入保留旧轮次、内容版本及已解决状态；已有共享状态时，同轮同版本合并，异版意见归档，内容不同的本地意见分别保留。已导入快照会被记录，相同快照刷新不会重放，删除的导入意见不会因此复活。导入失败提示并保留原数据；无版本记录的旧数组只能关联到首次导入时内容，无法追溯旧正文。

每台有旧意见的电脑都需在原浏览器、原站点地址打开相应文档一次。新地址无法读取旧 origin 的存储，服务端也不能主动读取其他电脑的 localStorage。已有页面升级后须刷新，才能使用共享保存链路。

## 问题二的根因与修改

仓库 README 和 INSTALL 已支持项目内文件通过绝对路径审查；实际全局指令仍要求生成稿发布到预览目录，并明确要求项目源文件另发布一份。这是模板更新没有进入生效配置，而非服务缺少绝对路径能力。

落盘抽查同时看到了两类证据：一份预览稿与项目 `docs/` 中同名文件内容完全一致，确认属于发布副本；最近两份预览稿在所检查项目目录中没有同名文件，只能说明未找到同名源文件，不能据此断言不存在其他名称的源文件。发布副本会脱离项目的原地更新和版本管理；仅将源稿放在预览目录也会造成归属问题。本次不将两种现象混为一个已证实事实，也不批量整理旧稿。

只调整生效全局指令、README、INSTALL 和首页/审查页提示：

- 项目方案默认写在项目约定文档目录，无约定时使用项目内 `docs/`。
- 用 `/_preview/locate?path=<编码后的绝对路径>` 获取 `page`，直接通过 `/_review?page=<编码后的 page>` 审查同一源文件。原文与相对资源直接从原目录读取。
- 后续按批注原地修改同一文件并沿用入口。仅临时独立稿使用预览目录，保留现有目录链接。

## 修复前后相同用例

原有 `npm test` 在修复前通过，说明此前未覆盖跨浏览器共享。先新增 `tests/shared.cjs` 在未修改源码上运行并保存失败记录，再用相同的五组用例验证修复。所有夹具和状态都在独立临时目录，不用日常预览目录写测试文档。

| 用例 | 修复前 | 修复后 |
| --- | --- | --- |
| 普通与绝对路径指向同一文件，两上下文并发新增互见 | 失败，各见自己的意见 | 通过，两条都保留 |
| 同名异目录隔离、项目文件无需复制、相对图片 | 通过 | 通过 |
| 刷新与服务重启后新客户端读取两条意见 | 失败 | 通过 |
| 项目原地更新、入口稳定、轮次历史跨客户端保留 | 失败 | 通过 |
| 本地旧意见从另一入口导入、保留原存储、删除后不重复导入 | 失败 | 通过 |

修复前保存请求记录为 `[]`；修复后实际出现 `POST /_preview/review`，随后另一上下文通过 GET 读到新状态。新批注不再依赖 localStorage；遗留 localStorage 仅用于保留与导入。

## 剩余限制

- 上述为同一主机的隔离浏览器上下文，使用实际局域网访问地址；未执行两台物理电脑的端到端网络验收。
- 没有访问用户日常浏览器真实 localStorage；旧数据迁移用合成数组及包含历史的旧对象验证。真实旧意见需按前述步骤逐浏览器导入。
- 状态目录由一个服务进程管理，不支持多进程共同写入；没有引入分布式锁或数据库。
- 更新通过轮询与窗口可见事件读取，不是即时同步。文档改名或移动会形成新身份；同路径原地修改保持原身份和审查入口。
- 后续 Agent 的实际新建文档行为尚需在新任务中观察；当前已验证生效文件、入口提示和项目内文档直接审查能力，未声称已证明所有后续 Agent 都会遵循新规则。
